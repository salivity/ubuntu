Using ssh-keyscan to Populate known_hosts on Ubuntu

This article explains the role of the ssh-keyscan utility on Ubuntu systems, focusing on how it gathers public SSH host keys to automate the population of known_hosts files. Readers will learn the mechanics behind the command, practical syntax for individual and bulk host key retrieval, common use cases in automation pipelines, and the critical security implications of bypassing manual fingerprint verification.

What Is ssh-keyscan?

ssh-keyscan is a standard command-line utility bundled with the OpenSSH client package on Ubuntu. Its primary function is to query remote SSH servers over the network and retrieve their public host keys. Unlike the standard ssh client, ssh-keyscan does not attempt to authenticate a user or start an interactive login session; it strictly requests and displays the server's public key data.

The Role of ssh-keyscan in Managing known_hosts

When connecting to an SSH server for the first time, OpenSSH prompts the user to verify the authenticity of the remote host. Once accepted, the key fingerprint is recorded in the user's ~/.ssh/known_hosts file (or the system-wide /etc/ssh/ssh_known_hosts file).

In automated workflows, continuous integration/continuous deployment (CI/CD) pipelines, or large-scale infrastructure provisioning, interactive prompts cause scripts to hang or fail. ssh-keyscan resolves this by allowing administrators to fetch remote host keys programmatically and append them directly to the appropriate known_hosts file, pre-populating trusted keys and preventing "Host key verification failed" errors.

Basic Syntax and Practical Examples

Scanning a Single Host

To scan a remote host and append its public key to your local known_hosts file, use standard shell redirection:

ssh-keyscan example.com >> ~/.ssh/known_hosts

To populate the system-wide file for all users on an Ubuntu machine:

sudo ssh-keyscan example.com >> /etc/ssh/ssh_known_hosts

Specifying Key Types

By default, modern versions of ssh-keyscan request all available key algorithms (such as RSA, ECDSA, and Ed25519). You can limit the output to a specific, modern algorithm using the -t flag:

ssh-keyscan -t ed25519 example.com >> ~/.ssh/known_hosts

Scanning Non-Standard Ports

If an SSH daemon listens on a port other than the default port 22, use the -p flag:

ssh-keyscan -p 2222 example.com >> ~/.ssh/known_hosts

Bulk Scanning from a File

For fleets of servers, you can provide a list of IP addresses or hostnames inside a text file using the -f flag:

ssh-keyscan -f /path/to/server_list.txt >> ~/.ssh/known_hosts

Security Considerations

While ssh-keyscan simplifies automation, it alters the default security model of SSH:

  • Trust on First Use (TOFU) Bypass: ssh-keyscan blindly accepts whatever public key the server provides at the moment of scanning. It does not authenticate that key against an authoritative source.
  • Man-in-the-Middle (MitM) Risks: If the scan is executed over an untrusted or compromised network, an attacker could intercept the connection and supply a malicious key.

To mitigate this risk, ssh-keyscan should ideally be run over secure, isolated networks (such as private VPCs or management subnets), or the retrieved fingerprints should be validated against known out-of-band host key values before relying on them in production environments.
