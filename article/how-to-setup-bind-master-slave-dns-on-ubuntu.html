How to Setup BIND Master-Slave DNS on Ubuntu

Setting up a master-slave DNS configuration using BIND on Ubuntu creates redundancy and improves domain name resolution reliability across your network. In this setup, the primary (master) server holds the authoritative DNS zone files and handles updates, while the secondary (slave) server automatically syncs copies of these records to handle query loads and provide failover support. This guide outlines the step-by-step process to install, configure, and verify a BIND9 master-slave pair on Ubuntu servers.

Prerequisites

  • Two Ubuntu servers on the same network:
    • Master Server IP: 192.168.1.10
    • Slave Server IP: 192.168.1.11
  • Domain Name: example.com
  • Sudo privileges on both servers

Step 1: Install BIND9 on Both Servers

Run the following commands on both the Master and Slave servers to update the package index and install BIND9 along with its utilities:

sudo apt update
sudo apt install bind9 bind9utils bind9-doc -y

Step 2: Configure the Master DNS Server

1. Edit Global Options

Open the global options file on the Master server to allow query access and set up listening interfaces:

sudo nano /etc/bind/named.conf.options

Ensure the configuration permits queries from your network:

options {
        directory "/var/cache/bind";

        recursion yes;
        allow-query { any; };

        forwarders {
                8.8.8.8;
                8.8.4.4;
        };

        dnssec-validation auto;
        listen-on-v6 { any; };
};

2. Define the Zone File

Edit /etc/bind/named.conf.local on the Master server to define the domain zone and authorize zone transfers to the Slave server IP (192.168.1.11):

sudo nano /etc/bind/named.conf.local

Add the following block:

zone "example.com" {
    type master;
    file "/etc/bind/zones/db.example.com";
    allow-transfer { 192.168.1.11; };
    also-notify { 192.168.1.11; };
};

3. Create the Forward Zone File

Create the directory for zone files and copy the default template:

sudo mkdir -p /etc/bind/zones
sudo cp /etc/bind/db.local /etc/bind/zones/db.example.com
sudo nano /etc/bind/zones/db.example.com

Configure the record details:

$TTL    604800
@       IN      SOA     ns1.example.com. admin.example.com. (
                              3         ; Serial (Increment this on changes)
                         604800         ; Refresh
                          86400         ; Retry
                        2419200         ; Expire
                         604800 )       ; Negative Cache TTL
;
; Name Servers
@       IN      NS      ns1.example.com.
@       IN      NS      ns2.example.com.

; A Records for Name Servers
ns1     IN      A       192.168.1.10
ns2     IN      A       192.168.1.11

; Host A Records
@       IN      A       192.168.1.10
web     IN      A       192.168.1.20

Step 3: Configure the Slave DNS Server

1. Define the Secondary Zone

On the Slave server, edit /etc/bind/named.conf.local to point to the Master server:

sudo nano /etc/bind/named.conf.local

Add the secondary zone configuration:

zone "example.com" {
    type slave;
    file "/var/cache/bind/db.example.com";
    masters { 192.168.1.10; };
};

Note: The zone file path points to /var/cache/bind/ because BIND needs write permissions to store synced zone files automatically.

Step 4: Validate and Restart BIND Services

1. Check Configuration Files

Run syntax checks on both servers to ensure there are no configuration errors.

On the Master server:

sudo named-checkconf
sudo named-checkzone example.com /etc/bind/zones/db.example.com

On the Slave server:

sudo named-checkconf

2. Restart BIND Services

Restart and enable the BIND service on the Master server first, then on the Slave server:

sudo systemctl restart bind9
sudo systemctl enable bind9

Step 5: Verify Zone Transfer

Check the logs on the Slave server to confirm that the zone file was transferred successfully from the Master:

sudo journalctl -u bind9 -f

Look for confirmation entries such as transfer of 'example.com/IN' from 192.168.1.10#53: Transfer completed.

Test DNS resolution from a client machine using dig against the Slave server:

dig @192.168.1.11 web.example.com

If configured correctly, the Slave server will return the resolved IP address (192.168.1.20).
