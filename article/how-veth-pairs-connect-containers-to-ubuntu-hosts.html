How Veth Pairs Connect Containers to Ubuntu Hosts

Virtual Ethernet (veth) pairs act as a bidirectional software tunnel that bridges the isolated network namespace of a container to the Ubuntu host's networking stack. This article explains the architectural role of veth pairs, detailing how they cross namespace boundaries, integrate with Linux bridges, and facilitate seamless packet transmission between containerized applications, the host system, and external networks.

The Concept of a Veth Pair

A veth (virtual ethernet) device is an interconnected pair of virtual network interfaces created by the Linux kernel. They function like the two ends of a physical Ethernet cable: whatever enters one interface automatically exits the other. In container runtimes such as Docker, Podman, and LXC running on Ubuntu, a veth pair is the foundational building block for container-to-host and container-to-container communication.

Crossing the Namespace Boundary

Ubuntu uses Linux network namespaces to isolate container processes, giving each container its own routing table, firewall rules, and network interfaces. By default, a newly created network namespace cannot communicate with the rest of the system.

To establish connectivity, the container runtime:

  1. Creates a linked veth pair in the host's default namespace (typically named something like vethXXXX and vethYYYY).
  2. Moves one end into the container’s isolated network namespace and renames it to a standard identifier, such as eth0.
  3. Leaves the peer interface (often labeled veth...) in the root (host) namespace.

Because the two ends remain intrinsically linked regardless of namespace assignment, traffic can pass between the isolated container environment and the host.

Integration with the Host Bridge

Leaving the host-side veth interface standalone is not enough for broader networking; it must be attached to a bridge interface on Ubuntu (such as docker0, cbr0, or a custom Linux bridge like br0).

The bridge functions as a virtual software switch. When the host-side veth interface is bound to this bridge:

  • Local Switching: The bridge allows multiple containers on the same host to communicate with each other at Layer 2.
  • Routing and NAT: The host's iptables or nftables rules apply Network Address Translation (NAT) to outgoing container packets, translating private container IP addresses into the Ubuntu host's routable IP address for internet access.

The Packet Flow Mechanism

When an application inside a container transmits data:

  1. Egress (Container to Outside): The container application sends a packet to its local eth0. The packet instantly emerges on the paired veth interface residing in the host namespace. The host bridge receives the frame, forwards it through the Ubuntu routing table, applies NAT/masquerading, and sends it out through the physical network interface card (NIC).
  2. Ingress (Outside to Container): Return traffic reaches the physical NIC, is de-NATted by the kernel, routed across the bridge, sent into the specific host-side veth endpoint, and immediately surfaces inside the container via its internal eth0.

Through this mechanism, veth pairs preserve strict network isolation while providing the high-throughput, low-overhead connectivity required for modern containerized infrastructure on Ubuntu.
