How Ubuntu Uses /etc/ssl/certs for Root Certificates

In Ubuntu and other Debian-based Linux distributions, the /etc/ssl/certs directory serves as the centralized, system-wide store for trusted Root Certificate Authorities (CAs). This directory enables applications, command-line utilities, and background services to verify TLS/SSL certificates presented by remote servers during encrypted connections. This article explains the architectural role of /etc/ssl/certs, how Ubuntu organizes individual and bundled certificates within it, and the automated tools used to maintain root trust safely.

The Core Function of /etc/ssl/certs

When a program such as curl, wget, or a Python script initiates a secure HTTPS or TLS connection, it must determine whether to trust the remote server's certificate. To do this, the client checks whether the server's certificate was issued by an entity in its local trust store.

On Ubuntu, the standard location configured for OpenSSL and system libraries to find these trusted root certificates is /etc/ssl/certs. By centralizing root authority data in this directory, Ubuntu prevents individual applications from needing to implement and maintain their own proprietary trust databases.

Internal Structure: Bundles and Hashed Symlinks

Inspecting /etc/ssl/certs reveals two primary mechanisms for certificate discovery:

  1. The Combined Bundle (ca-certificates.crt):
    Inside this directory sits ca-certificates.crt, a single concatenated file containing every trusted root certificate in PEM format. Many modern programming runtimes (like Go or Node.js) and utilities read this aggregated file directly to load all trusted roots into memory in a single read operation.

  2. Hashed Symlinks (<hash>.0):
    OpenSSL provides a directory-lookup feature that avoids parsing thousands of certificates on every connection. It uses the c_rehash utility to generate an eight-character hash based on the subject name of each certificate, creating a symlink named <hash>.<integer> pointing to the certificate file. When an application queries a specific CA by name, OpenSSL computes the hash and reads only the matching file in /etc/ssl/certs.

Automatic Population via update-ca-certificates

Administrators should not manually place or delete files directly in /etc/ssl/certs. The directory is dynamically generated and maintained by the ca-certificates package. The real sources of truth reside elsewhere in the filesystem:

  • /usr/share/ca-certificates/: Contains default root certificates vetted and maintained by Mozilla and distributed via standard Ubuntu package updates.
  • /usr/local/share/ca-certificates/: The designated location for custom, private, or internal enterprise root certificates added by system administrators.

Whenever certificates are added, updated, or removed, the administrator runs:

sudo update-ca-certificates

This utility reads the certificates from the source directories, regenerates /etc/ssl/certs/ca-certificates.crt, and creates or removes the necessary symbolic links and hash links in /etc/ssl/certs.

Managing and Customizing Trust

To add an internal enterprise root certificate to the Ubuntu trust store:

  1. Copy the certificate in .crt format to /usr/local/share/ca-certificates/.
  2. Execute sudo update-ca-certificates.
  3. Verify that the tool reports one added certificate and that a corresponding symlink appears inside /etc/ssl/certs.

To untrust a default CA, administrators use dpkg-reconfigure ca-certificates or modify /etc/ca-certificates.conf, deselecting the unwanted authority before rebuilding the store. This workflow ensures that system updates do not accidentally restore disabled or compromised certificates.
