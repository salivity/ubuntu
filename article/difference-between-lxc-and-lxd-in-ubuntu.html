Difference Between LXC and LXD in Ubuntu

Linux Containers (LXC) and Linux Container Daemon (LXD) are two closely related container technologies in Ubuntu, but they serve different layers of system virtualization. LXC acts as the foundational, low-level user-space interface for creating and managing individual system containers, while LXD is a modern, daemon-based container and virtual machine manager built on top of LXC. This article explains the architectural differences, features, usability, and ideal use cases for both LXC and LXD.

Understanding LXC (Linux Containers)

LXC is a lightweight, low-level virtualization technology that allows you to run multiple isolated Linux systems (containers) on a single control host. It directly uses Linux kernel features such as control groups (cgroups), process namespaces, and chroot to isolate processes without the overhead of running a full virtual machine hypervisor.

  • Architecture: LXC functions primarily as a set of tools, templates, library bindings (liblxc), and command-line utilities.
  • Operation: It operates directly on individual container configuration files and relies on manual setups for networking, storage, and resource allocations.
  • Control: Users interact directly with containers via specific low-level commands like lxc-create, lxc-start, and lxc-stop.

Understanding LXD (Linux Container Daemon)

LXD is a next-generation system container and virtual machine manager developed by Canonical. It does not replace LXC; instead, it uses LXC under the hood via liblxc to handle container creation while providing a much higher-level, feature-rich management layer.

  • Architecture: LXD runs as a background daemon (lxd) that exposes a REST API over a local Unix socket or network connection.
  • Operation: All operations are processed through the API, allowing local and remote client interactions using a single command-line tool (lxc).
  • Capabilities: In addition to managing system containers, LXD also manages full KVM-based virtual machines using the exact same API and CLI interface.

Key Differences

1. Architecture and API

  • LXC: Direct, file-based management without a centralized background daemon. Remote management requires external tooling or manual SSH automation.
  • LXD: Daemon-based with a fully documented REST API. This makes LXD natively network-aware and suitable for remote management and integration into orchestration tools.

2. User Experience and Interface

  • LXC: Uses older, individual commands (lxc-start, lxc-ls) requiring direct root access or complex unprivileged user mapping configurations.
  • LXD: Uses a single, unified command-line client (lxc). Command structures are consistent across local and remote instances (e.g., lxc launch, lxc list).

3. Management and Features

  • LXC: Provides basic container lifecycle control. Advanced features like storage pools or dynamic networking must be configured manually on the host.
  • LXD: Offers built-in management for storage pools (ZFS, Btrfs, LVM, Ceph), automatic network management (bridges, OVN), stateful live migration (via CRIU), automated snapshots, and hardware passthrough.

4. Security Defaults

  • LXC: Defaults to privileged containers unless explicitly configured otherwise by the administrator.
  • LXD: Defaults to unprivileged containers using user namespaces, isolating container root privileges from the host system root for enhanced security.

5. Multi-Node Support

  • LXC: Strictly operates on a per-host basis.
  • LXD: Native support for LXD Clustering, allowing multiple Ubuntu servers to be grouped into a single pool to manage containers across multiple hosts seamlessly.

Which Should You Choose?

Use LXC if you are developing low-level container software, embedding containers into custom Linux distributions, or require extreme minimalism without running background daemons.

Use LXD for standard deployment in Ubuntu environments, cloud infrastructure, local development, or enterprise environments where you need automated networking, advanced storage handling, container snapshots, remote administration, or unified management of containers and virtual machines.
