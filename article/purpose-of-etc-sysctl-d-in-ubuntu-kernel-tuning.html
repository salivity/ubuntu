Purpose of /etc/sysctl.d in Ubuntu Kernel Tuning

The /etc/sysctl.d/ directory in Ubuntu provides a modular, drop-in framework for configuring and persisting Linux kernel runtime parameters across system reboots. This article explains the architectural role of /etc/sysctl.d/, how it replaces and complements the legacy /etc/sysctl.conf file, the lexicographical precedence rules governing configuration files, and how system administrators can safely apply persistent kernel modifications.

Understanding Kernel Parameter Persistence

The Linux kernel exposes internal configuration options via the sysfs and procfs virtual filesystems, primarily under /proc/sys/. While administrators can alter these parameters temporarily using the sysctl command at runtime, any changes made directly to memory are reset upon reboot. Persistent kernel tuning requires saving configuration key-value pairs into files that system initialization services parse during the boot sequence. In Ubuntu, this task is managed primarily by systemd-sysctl.service.

Modularity Over Monolithic Design

Historically, persistent kernel settings were stored in a single monolithic file: /etc/sysctl.conf. While functional, a single configuration file causes maintenance challenges when multiple software packages, automation playbooks, or system administrators attempt to modify kernel parameters simultaneously.

The /etc/sysctl.d/ directory solves this by introducing modular configuration. Instead of editing a single global file:

  • Third-party packages install their required kernel settings without overwriting administrator changes.
  • Administrators can isolate specific optimizations (such as networking, virtual memory, or security hardenings) into separate, descriptive configuration files (e.g., 10-network-security.conf, 20-vm-tuning.conf).
  • Configuration management tools (such as Ansible, Puppet, or Salt) can deploy or remove individual configuration snippets cleanly.

Precedence and Execution Order

The systemd-sysctl service processes configuration files across several directories in a specific order of priority:

  1. /etc/sysctl.d/*.conf and /etc/sysctl.conf (Local administrator configurations)
  2. /run/sysctl.d/*.conf (Runtime transient configurations)
  3. /usr/lib/sysctl.d/*.conf (Vendor- and distribution-provided defaults)

Files placed inside /etc/sysctl.d/ override vendor defaults of the same filename located in /usr/lib/sysctl.d/.

Within /etc/sysctl.d/, files are parsed in lexicographical order (alphabetical and numerical). A two-digit numerical prefix is standard practice to dictate processing sequence (e.g., 10-, 60-, 99-). If the same parameter is set across multiple files, the last file read determines the final value applied to the kernel. Consequently, files prefixed with 99- (such as 99-sysctl.conf or 99-custom.conf) are loaded last, granting them the highest precedence among local configurations.

Applying Configuration Changes

To add custom kernel parameters using /etc/sysctl.d/, create a standard configuration file ending with .conf:

# /etc/sysctl.d/99-network-tuning.conf
net.ipv4.ip_forward = 1
net.core.somaxconn = 4096
vm.swappiness = 10

Once the file is saved, administrators do not need to reboot the server to apply the parameters. Running the following command forces the kernel to reload all configuration files across all sysctl.d directories immediately:

sudo sysctl --system

The system will parse the directories in order of precedence, apply the directives sequentially, and display the resulting active parameters to the console.
