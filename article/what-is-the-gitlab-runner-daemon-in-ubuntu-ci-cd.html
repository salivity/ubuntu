What Is the GitLab Runner Daemon in Ubuntu CI/CD?

The GitLab Runner daemon on an Ubuntu system acts as the execution engine for GitLab CI/CD pipelines. Operating as an lightweight background service, it continuously polls your GitLab instance for pending jobs, provisions the necessary environment, executes pipeline scripts, and transmits real-time logs and build results back to GitLab. Understanding its role involves looking at job management, execution modes, service integration within Ubuntu, and artifact handling.

Core Responsibilities of the Runner Daemon

1. Job Polling and Management

The daemon runs continuously in the background, utilizing long polling to communicate with the GitLab API over standard HTTP/HTTPS. When a pipeline is triggered:

  • The daemon identifies pending jobs tagged for its specific runner capabilities.
  • It requests job payloads, which include the repository code, script instructions, environment variables, and configuration settings defined in .gitlab-ci.yml.

2. Executor Provisioning and Task Execution

Once a job is assigned, the daemon initializes the execution environment based on the configured executor type:

  • Shell Executor: Runs pipeline commands directly on the Ubuntu host using the bash shell under a designated system user account.
  • Docker Executor: Interacts with the host’s Docker daemon to pull required container images, create isolated environments, and run pipeline steps inside containers.
  • VirtualBox/KVM Executors: Provisions isolated virtual machines on the Ubuntu host for jobs requiring full OS-level isolation.

3. Real-Time Log Streaming

During execution, the runner daemon captures stdout and stderr outputs from the script commands. It streams these terminal logs back to the GitLab server in real time, allowing developers to monitor progress and debug failures directly from the GitLab web interface.

4. Cache and Artifact Management

The daemon handles files produced during pipeline runs:

  • Caching: Downloads existing dependencies before job execution and uploads updated caches after completion to speed up subsequent pipeline runs.
  • Artifacts: Gathers designated build outputs (such as compiled binaries or test report files) and uploads them to GitLab storage upon job completion.

Systemd Integration on Ubuntu

On an Ubuntu platform, the GitLab Runner daemon installs as a native systemd service (gitlab-runner.service). This integration provides several administrative advantages:

  • Automatic Startup: The daemon starts automatically when the Ubuntu system boots up, ensuring pipeline availability without manual intervention.
  • Process Recovery: If the runner process encounters an unexpected error or crashes, systemd automatically restarts the daemon.
  • Service Control: Administrators can manage the daemon using standard system commands: 
    sudo systemctl start gitlab-runner
sudo systemctl stop gitlab-runner
sudo systemctl status gitlab-runner

Security and Permission Control

The daemon enforces security boundaries on the Ubuntu host. By default, it runs under a dedicated, unprivileged system user named gitlab-runner.

When executing shell jobs, commands run with the permissions of this user, preventing pipelines from modifying critical system files unless explicit sudo privileges are configured. When managing Docker containers, the gitlab-runner user must be added to the docker user group to interact with /var/run/docker.sock.
