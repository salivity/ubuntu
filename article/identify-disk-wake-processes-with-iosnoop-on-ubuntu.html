Identify Disk Wake Processes with iosnoop on Ubuntu

Hard drives entering and exiting standby mode are essential for energy saving and noise reduction, but background processes often wake them unexpectedly. This guide explains how to use iosnoop, a dynamic tracing utility from the BPF Compiler Collection (BCC), on Ubuntu to capture real-time disk input/output (I/O) events. By monitoring these events alongside I/O latency, you can easily identify the exact process name and Process ID (PID) responsible for spinning up a sleeping drive.

1. Install BCC Tools

iosnoop relies on eBPF (Extended Berkeley Packet Filter) to trace block device I/O at the kernel level. On Ubuntu, it is packaged within the BCC utilities.

Open a terminal and install the required packages:

sudo apt update
sudo apt install bpfcc-tools linux-headers-$(uname -r)

On Ubuntu, tools from this package are installed with the -bpfcc suffix to prevent name conflicts. The binary will be available as iosnoop-bpfcc located in /usr/sbin/.

2. Identify the Target Device

Before running the trace, identify the disk you want to monitor. Run:

lsblk

Locate the drive's name (for example, sdb or sdc). If the drive is already in standby, you can verify its power state using hdparm:

sudo hdparm -C /dev/sdX

If it reports standby, the drive is spun down.

3. Run iosnoop to Capture Disk Activity

Because terminal logging or writing output to the monitored drive could prevent it from remaining asleep, ensure your terminal or log file runs on an SSD or RAM disk (/tmp or /dev/shm).

Execute iosnoop-bpfcc with timestamps and disk queue latency:

sudo iosnoop-bpfcc -ts -d sdX

Replace sdX with your target drive (e.g., sdb). The flags provide critical information:

  • -t: Adds a timestamp to each I/O event.
  • -s: Adds the issue-to-complete duration (latency) in milliseconds.
  • -d sdX: Restricts tracing to the specified device.

If you are monitoring disk activity over an extended period (such as overnight), direct the output to a temporary RAM-backed location:

sudo iosnoop-bpfcc -ts -d sdX > /dev/shm/disk_wake.log

4. Locate the Culprit Process

When the drive wakes from standby, check the iosnoop output. It displays several columns:

  • TIME(s): Time elapsed since tracing started.
  • COMM: The executable/command name responsible for the request.
  • PID: The process ID.
  • TYPE: The type of operation (Read R or Write W).
  • BYTES: Transfer size.
  • LAT(ms): The duration between the request submission and completion.

The Spin-Up Indicator (High Latency)

A mechanical hard drive requires 3 to 15 seconds to spin up from a standby state to full speed. Therefore, the specific I/O request that triggers the wake event will display an exceptionally high latency (LAT(ms)), typically between 3000.00 and 15000.00 ms.

Subsequent reads and writes will have low latency (under 10.00 ms). The process listed under the COMM column on that initial high-latency line is the process that woke the drive.

5. Resolve Common Causes

Once you have identified the COMM and PID, address the offending service:

  • updatedb.mlocate: Disable the timer if index updates should not scan external drives (sudo systemctl stop mlocate.timer).
  • smartd: Configure /etc/smartd.conf with the -n standby directive so SMART queries do not spin up idle drives.
  • systemd-udevd: Adjust rules querying volume information.
  • File Managers / Indexers: Exclude mount points of secondary drives from desktop search utilities such as Tracker or Baloo.
