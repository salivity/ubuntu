Understanding PM2 ecosystem.config.js on Ubuntu

This article explains the purpose, functionality, and advantages of using a PM2 ecosystem.config.js file when managing Node.js applications on an Ubuntu server. You will learn how this configuration file simplifies deployment workflows, handles multiple environments, automates multi-process clustering, and centralizes runtime settings into a single, version-controlled file instead of relying on complex command-line arguments.

In a production Ubuntu environment, running Node.js applications directly via command-line arguments (such as pm2 start app.js -i max --name "api") quickly becomes inefficient and error-prone. The ecosystem.config.js file solves this by acting as a centralized, JavaScript-based configuration file that defines how PM2 should launch, monitor, and scale your Node.js processes.

Centralized Process Management

The primary role of the ecosystem file is defining one or more applications within an apps array. Instead of remembering specific startup parameters for every individual service, developers can define an application's name, entry script, working directory, and execution flags in a single place. Managing complex microservice architectures on an Ubuntu server is simplified to executing pm2 start ecosystem.config.js, which launches all configured services simultaneously.

Multi-Core Scaling and Cluster Mode

Node.js operates on a single thread by default. To take full advantage of multi-core Ubuntu servers, PM2 provides cluster mode. Inside ecosystem.config.js, you can configure the instances and exec_mode properties:

  • exec_mode: 'cluster': Enables load balancing across processes.
  • instances: 'max' (or a specific integer): Automatically spawns a process for each available CPU core.

This eliminates downtime during heavy traffic and ensures maximum hardware utilization.

Environment Variable Isolation

Managing development, staging, and production credentials directly in shell environments can lead to conflicts. The ecosystem file allows you to structure environment variables declaratively:

  • env: Default environment variables loaded on standard runs.
  • env_production: Production-specific variables activated by passing the --env production flag.

This ensures sensitive values, database connection strings, and ports are consistently applied across deployments without manual re-entry.

Automated Health and Resource Controls

Ubuntu servers require robust stability measures. The ecosystem configuration lets you declare strict recovery rules to prevent runaway processes from consuming server resources:

  • max_memory_restart: Automatically restarts an application if its RAM consumption exceeds a specified limit (e.g., '500M').
  • restart_delay and max_restarts: Protects the server from crash loops by staggering reboot attempts.
  • watch and ignore_watch: Automates process restarts on file changes while excluding directories like node_modules or logs.

Custom Log Routing

By default, PM2 stores logs in the user's home directory (~/.pm2/logs). With ecosystem.config.js, you can route standard output (out_file) and standard error (error_file) to dedicated application paths (such as /var/log/app/) and specify log formatting settings like time: true to append timestamps to every log line.

Deployment Automation

The ecosystem file includes a dedicated deploy block. This feature enables automated deployments directly to your Ubuntu server over SSH. It defines the repository, target host, SSH credentials, destination directory, and post-deployment commands (such as running npm install, compiling assets, and restarting the PM2 instances), turning the file into a lightweight continuous deployment pipeline.
