Purpose of /etc/resolv.conf Symlink in Ubuntu

In modern Ubuntu releases, /etc/resolv.conf is configured as a symbolic link rather than a static text file to seamlessly bridge legacy software with modern network management. Instead of requiring manual editing or static DNS entries, this symlink points to a dynamically generated file managed by systemd-resolved. This architecture allows Ubuntu to dynamically handle network configuration changes—such as switching Wi-Fi networks or connecting to a VPN—while providing local DNS caching, split-DNS routing, and backward compatibility for applications that still expect standard DNS configurations in /etc/resolv.conf.

Why Ubuntu Uses a Symlink for DNS Resolution

Historically, Linux operating systems stored global DNS server addresses directly inside /etc/resolv.conf. Any change to network adapters, DHCP configurations, or VPN connections required direct, often conflicting, writes to this file.

Starting with Ubuntu 16.04 and solidified in 18.04 LTS and later, Ubuntu adopted systemd-resolved as its default network name resolution daemon. To maintain system stability without breaking applications that hardcode reads to /etc/resolv.conf, Canonical turned the file into a symlink pointing into the /run/systemd/resolve/ runtime directory.

What the Symlink Points To

By default, /etc/resolv.conf links to:

/run/systemd/resolve/stub-resolv.conf

This stub configuration file contains a single local loopback IP address as the primary nameserver: 127.0.0.53.

When an application attempts to resolve a domain name:

  1. It reads /etc/resolv.conf via the symlink.
  2. It sends the DNS query to 127.0.0.53:53, where the systemd-resolved stub listener processes the request.
  3. systemd-resolved routes the request to the actual upstream DNS server configured for the active network interface.

Primary Roles of the Symlink Setup

1. Dynamic Network Adaptation

Modern computers frequently change networks, connect to VPNs, or switch between Ethernet and Wi-Fi. Because the target of the symlink resides in /run (a temporary filesystem cleared on boot), systemd-resolved can rewrite DNS routes on the fly without corrupting long-term disk state or leaving stale DNS entries behind.

2. Local DNS Caching and Performance

Routing DNS traffic through the local stub listener (127.0.0.53) enables built-in DNS caching. Frequently visited domain queries are answered locally from cache, reducing latency and saving network bandwidth.

3. Split-DNS and Multi-Interface Support

When connected to a corporate VPN, specific private domain queries (e.g., internal.company.com) must go to the VPN's DNS server, while public internet queries should go to the local network router. The systemd-resolved daemon natively handles this per-interface routing, which standard static /etc/resolv.conf files cannot do.

4. Backward Compatibility

Legacy software, C libraries (like glibc), and custom scripts expect to find nameserver directives in /etc/resolv.conf. The symlink ensures these legacy components continue to work out of the box while standardizing modern DNS processing under systemd.

Alternative Symlink Targets

While /run/systemd/resolve/stub-resolv.conf is the default, Ubuntu supports an alternative configuration depending on system needs:

  • /run/systemd/resolve/resolv.conf: This file bypasses the local 127.0.0.53 stub listener and directly lists the actual upstream DNS servers obtained via DHCP or manual interface configuration. It is typically used if an application is incompatible with local loopback DNS listeners.
