Ubuntu Netplan Scripts with networkd-dispatcher

In modern Ubuntu systems, Netplan functions as the default network configuration abstraction layer, relying on backends like systemd-networkd to manage active interfaces. Because Netplan does not natively support runtime hooks or pre-up/post-down scripts like the legacy ifupdown framework, administrators require an event-driven mechanism to execute custom code when interface states change. The networkd-dispatcher daemon fulfills this role by monitoring systemd-networkd over the system D-Bus and executing user-defined scripts in response to network interface transitions.

Why networkd-dispatcher Is Necessary

Netplan generates configuration files at boot or during network reloads, rendering definitions for systemd-networkd (the standard on Ubuntu Server) or NetworkManager (standard on Ubuntu Desktop). Once generated, Netplan ceases execution and relinquishes interface lifecycle management to the backend.

While the legacy /etc/network/interfaces setup provided directories like /etc/network/if-up.d/ to trigger hooks, systemd-networkd by itself does not have a direct file-system-based hook directory. The networkd-dispatcher service bridges this gap. It runs continuously as a systemd service, watching D-Bus signals emitted by systemd-networkd and triggering executable scripts placed in specific operational state directories.

Network States and Directory Structure

When networkd-dispatcher detects an interface state update, it inspects the corresponding subdirectories inside /etc/networkd-dispatcher/. Each directory maps directly to a lifecycle state reported by systemd-networkd:

  • configuring.d/: The interface is actively negotiating link or address configuration.
  • configured.d/: The interface has successfully received its addressing parameters (IP, netmask) but may not yet have an active default gateway.
  • routable.d/: The interface is fully configured, has a route to external networks, and is ready to transmit traffic. This is the modern replacement for legacy post-up scripts.
  • degraded.d/: The interface is operational but lacks a complete configuration (for example, missing an IPv6 address in a dual-stack configuration).
  • carrier.d/: A physical or data-link layer carrier has been detected.
  • dormant.d/: The interface is up at the network layer but not actively passing traffic (common in 802.1X authentication).
  • off.d/: The interface has been brought down or lost link.

Script Execution and Environment Variables

To run a custom script, place the executable into the folder corresponding to the targeted event (e.g., /etc/networkd-dispatcher/routable.d/my-script.sh).

For scripts to execute, they must meet standard permission requirements:

  1. They must be owned by root.
  2. They must have executable permissions set (chmod +x).
  3. They must begin with a valid shebang line (e.g., #!/bin/sh or #!/bin/bash).

When networkd-dispatcher runs a hook, it populates several environment variables that can be evaluated within the script:

  • $IFACE: The name of the network interface that triggered the event (e.g., eth0, enp3s0).
  • $STATE: The target state category matching the directory (e.g., routable, off).
  • $AdministrativeState: The administrative status of the interface (e.g., configured, unmanaged).
  • $OperationalState: The systemd operational status (e.g., routable, degraded).

Using these variables, a single script can filter execution so it only affects specific adapters, preventing unnecessary triggers when loopback or virtual bridge interfaces change states.
