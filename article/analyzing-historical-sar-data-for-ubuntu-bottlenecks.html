Analyzing Historical SAR Data for Ubuntu Bottlenecks

System Activity Reporter (SAR) is a powerful utility within the sysstat package that collects, reports, and saves system activity data over time. Analyzing historical SAR data in Ubuntu allows administrators to investigate past incidents, identify performance bottlenecks across CPU, memory, disk I/O, and network subsystems, and optimize system resource allocation based on actual usage patterns.

1. Locate Historical Data Files

Ubuntu stores binary SAR data files in the /var/log/sysstat/ directory by default.

  • The files are named saDD, where DD represents the day of the month (e.g., sa15 for the 15th).
  • Text-formatted daily reports are often saved as sarDD in the same directory.
  • If data collection was not previously active, enable it by setting ENABLED="true" in /etc/default/sysstat and restarting the service via sudo systemctl restart sysstat.

2. Specify Time Ranges for Analysis

To isolate a specific incident, filter the SAR readings using the start (-s) and end (-e) time parameters alongside the target file (-f).

sar -f /var/log/sysstat/sa15 -s 14:00:00 -e 15:30:00

3. Analyze CPU Performance

High CPU utilization or queuing indicates processor bottlenecks. Load average and individual CPU usage can be inspected using the -u and -q flags.

  • Command: sar -u -f /var/log/sysstat/saDD
  • Key Metrics:
    • %usr: Percentage of CPU used by user-level applications.
    • %sys: Percentage of CPU used by the kernel.
    • %iowait: Percentage of time the CPU was idle while waiting for I/O requests. High values point to disk or network storage latency rather than a CPU limitation.
    • %idle: Percentage of time the CPU was idle. Values consistently near 0% indicate CPU exhaustion.

Check queue length with sar -q -f /var/log/sysstat/saDD. A runq-sz significantly higher than the number of available CPU cores indicates thread contention.

4. Evaluate Memory and Swap Usage

Memory exhaustion leads to aggressive caching eviction or system swapping, severely slowing performance.

  • Command: sar -r -f /var/log/sysstat/saDD (RAM) and sar -S -f /var/log/sysstat/saDD (Swap)
  • Key Metrics:
    • %memused: Percentage of total memory used.
    • %swpused: Percentage of swap space used.
    • kbcommit: Amount of memory needed for the current workload; exceeding total RAM indicates overcommit.

If %swpused increases over time alongside high swapping activity, the system requires more physical RAM or process optimization.

5. Detect Disk I/O Bottlenecks

Slow disk access often impacts overall system responsiveness. Use the -b flag for general I/O statistics and -d for per-device metrics.

  • Command: sar -d -p -f /var/log/sysstat/saDD
  • Key Metrics:
    • tps: Transfers per second.
    • await: Average time (in milliseconds) for I/O requests to be served. High await times (e.g., >10–20ms on SSDs) indicate storage bottlenecks.
    • %util: Percentage of CPU time during which I/O requests were issued to the device. Values close to 100% indicate device saturation.

6. Inspect Network Activity

Network bottlenecks can manifest as dropped packets or saturated bandwidth capacity.

  • Command: sar -n DEV -f /var/log/sysstat/saDD
  • Key Metrics:
    • rxkB/s and txkB/s: Kilobytes received and transmitted per second. Compare these against interface bandwidth limits.
    • rxpck/s and txpck/s: Total packets received and transmitted per second.

To check for errors or dropped packets, run sar -n EDEV -f /var/log/sysstat/saDD.

7. Correlate System Metrics

To accurately identify the root cause of a bottleneck, compare findings across metrics during the same timeframe:

  1. High %iowait + High %util on a disk device = Storage/Disk Bottleneck.
  2. High %usr or %sys + Low %iowait + High runq-sz = CPU Bottleneck.
  3. High %memused + Increasing %swpused + High I/O await = Memory Exhaustion (Swapping) Bottleneck.
