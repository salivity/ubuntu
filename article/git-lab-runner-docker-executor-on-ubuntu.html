GitLab Runner Docker Executor on Ubuntu

This article examines the role of the GitLab Runner Docker executor when building CI/CD jobs on an Ubuntu system. It covers the core functionality of the executor, its architecture and execution lifecycle, the benefits of containerized isolation over shell-based execution, and key configuration practices for optimizing build pipelines on Ubuntu.

What is the Docker Executor?

The GitLab Runner Docker executor is an execution environment that runs CI/CD jobs inside isolated Docker containers. When configured on an Ubuntu host, the runner uses the local Docker engine daemon to provision a clean container for each job defined in your .gitlab-ci.yml pipeline, executes the specified commands, extracts artifacts, and terminates the container upon completion.

Primary Roles and Functions

1. Environment Isolation and Reproducibility

Unlike the standard Shell executor, which executes commands directly on the host Ubuntu operating system, the Docker executor isolates each pipeline run inside a self-contained container. This guarantees:

  • Clean State: Every job starts in an immutable environment, preventing residual artifacts or temporary files from affecting subsequent runs.
  • No Host Pollution: Build dependencies, packages, and custom libraries are installed inside the container, leaving the underlying Ubuntu server clean and stable.
  • Consistency: Developers can define the exact runtime environment (e.g., Node.js, Python, Golang, or specific Ubuntu versions) directly in the pipeline configuration, ensuring identical execution across local and remote environments.

2. Multi-Language and Multi-Version Flexibility

A single Ubuntu host running GitLab Runner can simultaneously handle diverse projects requiring conflicting software versions. One job can run inside a container using Python 3.8, while another runs using Python 3.12, without necessitating multiple runtime installations or complex environment managers on the Ubuntu host.

3. Service Orchestration

The Docker executor can link sidecar containers to the primary build container using the services keyword in .gitlab-ci.yml. This allows jobs to easily interface with disposable databases (e.g., PostgreSQL, MySQL) or caching systems (e.g., Redis) that are automatically spun up and torn down alongside the job.

4. Security and Sandboxing

Because commands are executed within a container, malicious or erroneous scripts are restricted to the containerized environment. This shields the host Ubuntu kernel, file system, and network services from accidental destruction or unauthorized access, provided the container is not running in privileged mode.

How the Docker Executor Works on Ubuntu

When a job is triggered, the interaction between GitLab Runner and Ubuntu follows a distinct lifecycle:

  1. Job Dispatch: The GitLab Runner daemon on Ubuntu polls the GitLab instance and receives a job assignment.
  2. Image Pulling: The runner communicates with the local Docker daemon (/var/run/docker.sock) to pull the designated Docker image from Docker Hub or a private container registry.
  3. Container Creation: Docker initializes the build container and any specified service containers on a private bridge network.
  4. Code Checkout: The runner clones the repository into the container via an automatically created volume mount.
  5. Execution: The commands defined in the before_script and script sections execute sequentially inside the container.
  6. Artifact Upload: Generated artifacts or cache files are compressed and sent back to GitLab.
  7. Cleanup: The Docker daemon stops and removes the job containers, releasing compute and memory resources back to the Ubuntu host.

Essential Configuration on Ubuntu

The runner’s behavior is defined in /etc/gitlab-runner/config.toml on the Ubuntu host. A standard Docker executor configuration includes:

[[runners]]
  name = "ubuntu-docker-runner"
  url = "https://gitlab.com/"
  token = "RUNNER_TOKEN"
  executor = "docker"
  [runners.custom_build_dir]
  [runners.docker]
    tls_verify = false
    image = "ubuntu:22.04"
    privileged = false
    disable_entrypoint_overwrite = false
    oom_kill_disable = false
    disable_cache = false
    volumes = ["/cache"]
    shm_size = 0
  • image: Sets the default fallback image if none is specified in .gitlab-ci.yml.
  • privileged: When set to false, it protects the host Ubuntu kernel. It is only set to true when implementing Docker-in-Docker (DinD) for building container images within the CI/CD pipeline.
  • volumes: Manages caching between jobs to improve execution speed by persisting package managers' download directories.
