What Is DRBD in Ubuntu Clustering?

The Distributed Replicated Block Device (DRBD) is a software-based, shared-nothing storage solution designed to provide high availability and data redundancy in Linux environments. In an Ubuntu cluster, DRBD functions as a network-based equivalent of RAID 1, mirroring block devices across separate nodes in real time. This article covers the fundamental purpose of DRBD, how it integrates with Ubuntu clustering stacks, and why it is a critical component for building fault-tolerant services without dedicated shared storage hardware.

Network RAID 1 and Data Mirroring

At its core, DRBD operates directly above the physical block devices (such as hard drives, SSDs, or LVM logical volumes) and below the filesystem. When an application writes data to an Ubuntu system configured with DRBD, the DRBD kernel driver intercepts the write request. It writes the data to the local disk while simultaneously transmitting it over the network to the secondary node's storage.

This design creates a synchronized storage layer across independent physical servers. If the primary node experiences hardware failure, the secondary node already possesses an identical, up-to-date copy of the data, preventing data loss.

Eliminating the Need for Expensive Shared Storage

Traditional high-availability clusters often rely on centralized shared storage systems, such as a Storage Area Network (SAN) or Network Attached Storage (NAS). While effective, these solutions introduce high hardware costs, complex networking fabrics, and potential single points of failure if the storage array itself goes down.

DRBD enables a "shared-nothing" architecture. Each Ubuntu cluster node uses its own local drives, and DRBD provides the replication layer over standard Ethernet or high-speed InfiniBand connections. This drastically reduces infrastructure costs while maintaining enterprise-grade redundancy.

Integration with Pacemaker and Corosync

On Ubuntu Server, high-availability clusters are typically managed using Corosync for cluster membership and messaging, alongside Pacemaker for resource management. DRBD integrates natively into this stack:

  • Primary/Secondary Roles: In a standard active/passive setup, the primary node has read/write access to the DRBD device and mounts the filesystem. The secondary node continuously receives replicated data in the background without mounting the device.
  • Automated Failover: If the active node crashes, Corosync detects the node loss, and Pacemaker promotes the secondary node's DRBD device to the primary role. Pacemaker then mounts the filesystem on the secondary node and restarts critical services (such as MySQL, PostgreSQL, or web servers) with minimal disruption.
  • Dual-Primary Mode: DRBD also supports dual-primary configurations, where both nodes can read and write simultaneously. This mode is typically used alongside distributed cluster filesystems like OCFS2 or GFS2 to enable active/active clustering.

Replication Modes for Performance and Integrity

DRBD supports three distinct replication protocols to balance data integrity against network latency:

  1. Protocol A (Asynchronous): The write is considered complete once written to the local disk and queued in the local network buffer. This provides the highest performance and is ideal for long-distance disaster recovery, though it carries a slight risk of data loss during an abrupt crash.
  2. Protocol B (Memory-Synchronous): The write completes once stored locally and confirmed to have reached the remote node’s network buffer.
  3. Protocol C (Synchronous): The write is only acknowledged after it has been safely committed to disk on both the local and remote nodes. This is the standard choice for Ubuntu high-availability clusters, ensuring absolute data consistency and zero data loss between nodes.

Summary

The primary purpose of DRBD in an Ubuntu cluster is to provide a reliable, cost-effective, block-level replication mechanism. By synchronizing local storage across nodes over the network, it eliminates single points of failure, facilitates seamless automated failover with Pacemaker, and ensures business continuity for mission-critical applications.
