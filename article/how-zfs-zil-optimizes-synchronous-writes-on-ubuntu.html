How ZFS ZIL Optimizes Synchronous Writes on Ubuntu

This article explains the critical role of the ZFS Intent Log (ZIL) and dedicated Separate Intent Log (SLOG) devices in accelerating synchronous write performance on Ubuntu systems. You will learn the difference between synchronous and asynchronous writes, why standard storage pools experience severe bottlenecks during database or virtual machine operations, and how deploying a dedicated high-speed log drive resolves latency issues while guaranteeing complete data integrity during power failures.

Understanding Synchronous Writes and the Default ZIL

In ZFS, disk writes are categorized into two types: asynchronous and synchronous.

  • Asynchronous writes are held in system RAM within a Transaction Group (TXG) and batched to the storage pool every few seconds. This provides maximum throughput but risks losing several seconds of uncommitted data during a sudden power loss.
  • Synchronous writes (triggered by flags like O_SYNC or system calls like fsync) demand guaranteed persistence. Applications such as PostgreSQL, MySQL, NFS shares, and Proxmox/KVM virtualization require confirmation that data is physically written to non-volatile storage before proceeding to the next operation.

To satisfy synchronous write requirements without forcing an entire TXG commit to disk, ZFS uses the ZFS Intent Log (ZIL). By default, the ZIL is not a separate physical device; it is dynamically carved out from the standard storage pool disks.

When a synchronous write occurs in a default configuration, the mechanical hard drives or standard SSDs must rapidly write the log entry to the main pool, wait for confirmation, and return a success signal to the application. This causes severe disk head contention on HDDs and induces massive write latency, heavily throttling system performance.

The Purpose of a Dedicated ZIL (SLOG) Drive

A dedicated ZIL drive—technically referred to as a Separate Intent Log (SLOG)—removes this bottleneck by offloading the intent log from the main data pool to a dedicated, high-speed storage device.

When you attach an SLOG device to a ZFS pool on Ubuntu, the workflow changes:

  1. A synchronous write request arrives from an application (e.g., a database transaction).
  2. ZFS simultaneously places the data into system RAM for the upcoming TXG batch and writes a minimal log record directly to the dedicated SLOG drive.
  3. Because the SLOG is an ultra-fast, low-latency device, the log write completes almost instantly.
  4. ZFS immediately sends an acknowledgment back to the application, allowing it to continue processing without waiting.
  5. At the regular TXG commit interval (usually every 5 seconds), the actual data is written to the primary storage pool directly from RAM in an efficient, sequential pass.
  6. Once the TXG is written to the main pool, the log entries on the SLOG are invalidated.

Under normal operating conditions, data is never read from the SLOG drive. It serves exclusively as a high-speed write buffer. The only time ZFS reads from the SLOG is during system recovery following an abrupt shutdown or kernel crash, replaying the uncommitted transactions into the main pool.

Hardware Requirements for an Effective Ubuntu SLOG

Adding just any standard consumer SSD as an SLOG will not yield optimal performance and may even degrade pool speed. A proper SLOG drive requires:

  • Power Loss Protection (PLP): The drive must have onboard capacitors to flush its internal controller cache to NAND flash during a sudden power outage. Drives without PLP often disable their write caches for synchronous requests, resulting in extremely poor write speeds.
  • Low Write Latency: Enterprise NVMe drives, such as Intel Optane (3D XPoint) or enterprise U.2/U.3 SSDs, provide sub-millisecond sync latencies that consumer flash drives cannot match.
  • High Write Endurance: The ZIL is subject to constant, relentless writes. Enterprise-grade write endurance (measured in Drive Writes Per Day, or DWPD) is essential to prevent premature drive failure.
  • Small Capacity Needs: Because the ZIL only needs to store enough data to cover two to three TXG commit windows (roughly 5 to 10 seconds of maximum throughput), the device does not need to be large. A 16GB to 64GB partition is typically more than sufficient for most workloads.

Summary of Benefits on Ubuntu

Configuring a dedicated ZIL device on an Ubuntu ZFS deployment isolates latency-sensitive operations from main pool I/O. It eliminates the disk thrashing associated with synchronous writes on spinning rust, dramatically lowers application wait times for NFS and database transactions, and maintains strict POSIX compliance and data safety without sacrificing overall storage performance.
