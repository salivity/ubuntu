How to Debug Crashing Applications with strace in Ubuntu

The strace utility is a powerful diagnostic tool in Ubuntu used to monitor the interaction between a user-space application and the Linux kernel. When an application crashes silently or throws generic error messages, strace captures every system call—such as file reads, memory allocations, and network connections—allowing you to pinpoint the exact failure point. This guide covers how to install strace, capture system calls during an application crash, filter output for specific signals or errors, and interpret log files to resolve missing dependencies, permission issues, or memory errors.

Installing strace on Ubuntu

strace is available in the official Ubuntu repositories. Open your terminal and install it using apt:

sudo apt update
sudo apt install strace

Verify the installation by checking the version:

strace -V

Running an Application Under strace

To diagnose a crashing program, pass the program's executable path directly to strace.

strace ./my_failing_app

Because strace outputs system calls directly to stderr, the screen can fill quickly with text. Save the trace output to a file for easier analysis using the -o flag:

strace -o crash_debug.log ./my_failing_app

If the application requires administrative privileges, prefix the command with sudo:

sudo strace -o crash_debug.log ./my_failing_app

Attaching strace to a Running Process

If a process is freezing or crashing while running in the background, you can attach strace to its Process ID (PID).

  1. Find the PID of the application:
pgrep my_failing_app
  1. Attach strace using the -p option:
sudo strace -p <PID> -o running_app.log

Press Ctrl+C to detach strace when you are done capturing data.

Tracing Child Processes and Threads

Many modern applications spawn multiple processes or threads. By default, strace only tracks the main process. Use the -f flag to follow child processes created by fork or vfork calls:

strace -f -o multi_process.log ./my_failing_app

Analyzing the Output to Identify Crashes

When an application crashes, the root cause is almost always near the end of the generated output log. Use tail to view the final system calls before termination:

tail -n 50 crash_debug.log

Common Crash Indicators in strace Logs

  1. Signals (e.g., SIGSEGV or SIGABRT): Segmentation faults or abort signals appear right before the process exits.

    --- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=0x0} ---
+++ killed by SIGSEGV (core dumped) +++

    This indicates the program attempted to read or write to unallocated memory address 0x0 (null pointer dereference).

  2. Missing Files or Libraries (ENOENT): If an application crashes due to a missing configuration file or library, look for openat or access calls returning ENOENT (No such file or directory).

    openat(AT_FDCWD, "/etc/myapp/config.json", O_RDONLY) = -1 ENOENT (No such file or directory)

  3. Permission Denied (EACCES): If an app lacks read or write access to a resource:

    openat(AT_FDCWD, "/var/log/myapp.log", O_WRONLY|O_CREAT, 0644) = -1 EACCES (Permission denied)

Filtering Useful System Calls

To reduce clutter, filter for specific types of system calls using the -e flag.

Trace Only File Operations

To inspect missing configuration files or corrupted dynamic libraries:

strace -e trace=file ./my_failing_app

Trace Specific System Calls

To restrict monitoring to openat, read, and write calls:

strace -e trace=openat,read,write ./my_failing_app

Trace Network Calls

If the crash occurs during network initialization or sockets:

strace -e trace=network ./my_failing_app

Summary of Useful strace Command Options

  • -o <file>: Redirects output to a file.
  • -f: Follows child processes/threads.
  • -p <PID>: Attaches to an existing process ID.
  • -e trace=<category>: Filters output by system call type (e.g., file, network, process, memory).
  • -t or -tt: Adds timestamps to each line to help identify hangs or delays.
  • -c: Generates a summary histogram of time, calls, and errors per system call upon exit.
