How to Debug Core Dumps Using GDB in Ubuntu

Analyzing a core dump in Ubuntu using the GNU Debugger (GDB) involves enabling system core file generation, installing GDB, acquiring the crash log alongside the exact compiled executable, and inspecting the crash state using debugging commands. This guide outlines the end-to-end configuration process for configuring Ubuntu to capture core dumps and loading them into GDB for root-cause analysis.

Step 1: Enable Core Dumps in Ubuntu

By default, Ubuntu limits core dump file sizes to zero. You must increase this limit to allow the system to write core files upon a program crash.

  1. Open a terminal session.

  2. Set the maximum core dump size to unlimited for the current session:

    ulimit -c unlimited

  3. To make this change permanent across system reboots, edit /etc/security/limits.conf:

    sudo nano /etc/security/limits.conf

  4. Add the following lines at the end of the file:

    * soft core unlimited
* hard core unlimited

Step 2: Configure Systemd Core Dump Settings

Modern Ubuntu releases use systemd-coredump to capture crash reports.

  1. Install the utility if it is not present:

    sudo apt update
sudo apt install systemd-coredump

  2. Verify where core dumps are stored by checking /proc/sys/kernel/core_pattern. If configured via systemd, it typically pipes output directly to systemd utilities.

Step 3: Install GDB and Debugging Symbols

To effectively analyze a core dump, install GDB along with the debug symbols for your application.

  1. Install GDB:

    sudo apt install gdb

  2. Ensure your executable is compiled with debugging symbols enabled. If compiling with gcc or g++, append the -g flag:

    gcc -g -o my_app main.c

Step 4: Locate the Core Dump File

If a application crashes, retrieve the generated core file using coredumpctl or check the default storage directory:

  1. List recent core dumps managed by systemd:

    coredumpctl list

  2. Extract the relevant core file to your working directory:

    coredumpctl dump PID_OR_EXE_NAME --output core.dump

Alternatively, if systemd-coredump is not active, look for a file named core or core.<PID> in the directory where the application was executed.

Step 5: Launch GDB with the Executable and Core Dump

Run GDB by providing the path to the compiled binary followed by the path to the core dump file:

gdb /path/to/executable /path/to/core.dump

Step 6: Analyze the Crash in GDB

Once GDB loads, use standard commands to investigate the state of the program at the moment of failure:

  • View the backtrace: Print the call stack leading to the crash:

    bt

    or for full detail on local variables:

    bt full

  • Inspect specific frames: Switch to a specific frame number from the backtrace:

    frame <frame-number>

  • Print variable values: Check variable states at the time of the crash:

    print <variable-name>

  • Exit GDB:

    quit
