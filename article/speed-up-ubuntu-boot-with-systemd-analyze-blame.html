Speed Up Ubuntu Boot with systemd-analyze blame

The systemd-analyze blame command is a built-in Ubuntu diagnostic tool designed to profile the boot process by listing every active system service in descending order of initialization time. By highlighting the specific background daemons and startup scripts that take the longest to load, it provides system administrators with the exact data needed to pinpoint bottlenecks. Armed with this information, users can safely disable, delay, or reconfigure non-essential services to significantly reduce Ubuntu boot times.

How systemd-analyze blame Works

When an Ubuntu system powers on, the systemd init system orchestrates the loading of essential components, drivers, and background daemons. The systemd-analyze blame command parses the timestamps logged by systemd during the most recent startup sequence.

When executed in the terminal:

systemd-analyze blame

The tool outputs a clean, sorted list displaying the time taken by each unit file to initialize. Services taking seconds or tens of seconds appear at the very top, while instantaneous services are positioned at the bottom.

Pinpointing Boot Bottlenecks

The primary role of systemd-analyze blame in boot optimization is discovering unnecessary or slow-loading services. Common culprits revealed by the command include:

  • NetworkManager-wait-online.service: Often waits indefinitely or for long timeouts until a stable network connection is confirmed.
  • snapd.seeded.service: Scans and initializes Canonical Snap packages, which can introduce delays on mechanical hard drives or low-resource machines.
  • apt-daily.service: Periodically checks for software updates immediately after system initialization.
  • ModemManager.service: Probes for broadband cellular modems, a feature obsolete for the vast majority of standard desktop and server installations.

Interpreting the Output Correctly

While systemd-analyze blame is vital for optimization, understanding how systemd handles startup tasks is critical. systemd initializes many services in parallel. Therefore, a service that takes ten seconds to launch does not necessarily delay the entire boot process by ten seconds if it is running concurrently alongside other processes without blocking the login screen.

To verify whether a slow service highlighted by blame is actively holding up the boot timeline, administrators often cross-reference the output with:

systemd-analyze critical-chain

This companion command highlights the dependency chain that directly impacts the time it takes to reach the graphical desktop or login prompt.

Optimizing the System Based on Blame Output

Once systemd-analyze blame exposes the slowest services, users can take corrective actions depending on the role of each service:

  1. Disabling Unneeded Services: If a high-latency service is not required for daily operations (such as ModemManager.service), it can be disabled from starting automatically at boot: 
    sudo systemctl disable ModemManager.service
  2. Masking Problematic Units: If a service repeatedly activates due to hard dependencies from other packages, masking completely prevents it from starting: 
    sudo systemctl mask NetworkManager-wait-online.service
  3. Deferring Background Work: Non-critical background maintenance tasks can be converted into systemd timers configured to run several minutes after system startup, moving the resource load away from the primary boot phase.

By serving as the initial discovery layer for system diagnostics, systemd-analyze blame transforms boot optimization from guesswork into an accurate, targeted process.
