Role of rpcbind in Ubuntu NFS File Sharing

This article explains the function of the rpcbind service within a Network File System (NFS) deployment on Ubuntu. It covers how rpcbind acts as a port mapper to connect clients to dynamic server-side RPC services, details the difference in dependency between NFSv3 and NFSv4, and demonstrates basic commands to inspect and manage the service on an Ubuntu system.

What is rpcbind?

The rpcbind utility is a critical component of the Remote Procedure Call (RPC) architecture. In Linux environments like Ubuntu, it acts as a dynamic directory service that maps RPC program numbers to the specific universal network addresses and TCP/UDP port numbers where those services are currently listening. The service itself standardizes on well-known port 111 (both TCP and UDP).

How rpcbind Facilitates NFS Communication

NFS is built upon the Open Network Computing Remote Procedure Call (ONC RPC) protocol. Under standard operations—especially in legacy implementations—NFS does not assign static port numbers to its auxiliary sub-services. Instead, the process works as follows:

  1. Service Registration: When the NFS daemon and its related sub-services (such as mountd, statd for file locking, and lockd) start on the Ubuntu server, they bind to randomly assigned or available dynamic ports.
  2. Cataloging Ports: Upon startup, these services notify the local rpcbind daemon of their assigned port numbers and their corresponding RPC program IDs.
  3. Client Inquiries: When a client wishes to mount a remote directory, it first contacts the Ubuntu server's rpcbind service on port 111 to ask: "On which port is the mount daemon (mountd) running?"
  4. Connection Handshake: The rpcbind daemon responds with the appropriate port number. The client then establishes a direct connection to that specific port to complete the mount request and negotiate file access.

Without rpcbind, clients using RPC-dependent protocols have no automated method to discover which ports are handling authentication, lock management, or mount requests on the host.

NFSv3 vs. NFSv4 Reliance

The necessity of rpcbind depends significantly on the NFS protocol version deployed:

  • NFSv3: Strictly requires rpcbind. NFSv3 utilizes separate daemons for mounting (mountd), network lock management (lockd), and network status monitoring (statd), all of which rely on dynamic ports that must be resolved through rpcbind.
  • NFSv4: Minimizes the role of rpcbind. NFSv4 consolidates file operations, locking, and mounting into a single protocol flow operating over standard TCP port 2049. While a pure NFSv4 setup can function without rpcbind, Ubuntu typically keeps the service enabled to ensure backward compatibility with older clients and to support standard NFS administration tools.

Managing rpcbind on Ubuntu

On Ubuntu, rpcbind is provided by the package of the same name and is installed automatically as a dependency of nfs-kernel-server or nfs-common.

To check the operational status of rpcbind:

sudo systemctl status rpcbind

To view all active RPC-based services currently registered with rpcbind and their assigned ports, run:

rpcinfo -p

This output displays the program number, version, transport protocol (TCP/UDP), port, and service name (such as nfs, mountd, or nlockmgr), confirming that the Ubuntu server is ready to route incoming client connections to the appropriate NFS sub-processes.
