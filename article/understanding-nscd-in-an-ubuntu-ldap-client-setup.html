Understanding nscd in an Ubuntu LDAP Client Setup

The Name Service Cache Daemon (nscd) is a background service in Linux designed to optimize system performance by caching local and remote Name Service Switch (NSS) queries. In an Ubuntu LDAP client configuration, nscd plays a vital role by temporarily storing lookup results for users, groups, and hosts, dramatically reducing network traffic and query latency to the central LDAP directory. This article explains the primary functions of nscd, its benefits in LDAP environments, and key operational considerations when deploying it on Ubuntu.

Reducing LDAP Server Load and Network Latency

Every time a command is executed that checks permissions, ownership, or user identity (such as ls -l, top, or authentication workflows), the operating system queries the NSS subsystem. When an Ubuntu system uses LDAP for centralized authentication via nss-ldap or libnss-ldapd, each of these lookups triggers a network request to the remote LDAP server.

Without caching, high-frequency queries can saturate network bandwidth and degrade directory server performance. nscd intercepts these lookup requests, returns cached results immediately for subsequent calls, and prevents redundant LDAP queries.

Supported Databases in LDAP Setups

nscd provides configurable caching for several standard NSS databases, the most critical for LDAP environments being:

  • passwd: Caches user identity records, including usernames, UIDs, and default shells.
  • group: Caches group names, GIDs, and group memberships, which significantly speeds up permission evaluations.
  • hosts: Caches DNS and hostname lookups.
  • services: Caches network service mapping.

Each database has its own Time to Live (TTL) settings within /etc/nscd.conf, dictating how long an entry remains valid before a new query must be forwarded to the LDAP directory.

Managing Negative Lookups

nscd also performs negative caching, which stores failed lookups (for example, queries for users or groups that do not exist). If a non-existent account is repeatedly queried by a script or service, nscd answers locally that the record does not exist instead of repeatedly querying the LDAP server.

Limitations and the Shift Toward SSSD

While nscd effectively reduces load, it has limitations in modern deployments:

  • Stale Data: Changes made directly on the LDAP server (such as group reassignment or user termination) are not recognized locally until the cache expires or the daemon is flushed using nscd -i <database>.
  • No Offline Authentication: nscd does not handle full credential validation or secure offline authentication states.
  • SSSD as the Modern Alternative: On modern Ubuntu releases, the System Security Services Daemon (sssd) is typically preferred over nscd for LDAP integrations. sssd provides built-in caching, offline authentication, and Kerberos management. Running nscd concurrently with sssd can cause conflicts and is generally discouraged.
